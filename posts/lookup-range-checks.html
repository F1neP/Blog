Lookup Arguments 与 Range Checks：现代 ZK 电路的约束加速器

PROOF SYSTEMS · TABLE MEMBERSHIP

范围检查、字节运算、状态机和哈希 S-box 都可以写成大量低度约束，但成本往往很高。Lookup argument 把问题改写为“witness 中若干行属于一张合法表”，再用随机压缩与多重集合等价证明批量成员关系。

为什么需要这一章？

范围、字节、位运算和状态转换若全部展开成普通算术门，约束数会迅速膨胀。Lookup 论证把这些条件改写为“查询值属于预先承诺的表”，但还必须证明多重集合关系而非只检查几个点；本章解释这一效率来源及其边界。

Lookup 只证明表成员关系。它不会自动证明 table 本身正确、query 来自正确业务变量，或多 limb 重组没有模回绕。

六、三类严重错误

Red-team checklist
  • 元组列未联合压缩：允许从合法行中拼出非法组合。
  • Multiplicity/排序未约束：查询遗漏、重复或伪造元素仍可能通过集合检查。
  • 范围重组溢出：每个 limb 均在范围内，但总值在域中模回绕而不等于目标整数。
一句话总结：Lookup argument 用随机压缩保持同一行元组，再通过多重集合等价批量证明查询属于合法表；它能显著降低范围与非线性操作成本，但不能替代 query-to-program 和 table correctness 的约束。

七、Lookup 的可靠性、成本与适用边界

CORRECTNESS

成员正确性

每个查询值都应来自同一版本、同一列语义的允许表。

MULTIPLICITY

重数完整性

重复 witness 值不能在压缩或排序时被丢失。

BINDING

元组绑定

多列压缩必须包含列位置、表身份和随机挑战，避免跨列替换。

TRADEOFF

成本权衡

表越大，预处理、承诺和内存成本越高；小范围位分解有时更简单。
