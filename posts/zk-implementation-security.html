零知识证明实现安全：从欠约束到 Transcript 绑定

PROOF SYSTEMS · RED-TEAM CHECKLIST

一个密码学上可靠的证明系统可以忠实证明一个错误关系。实际漏洞通常发生在四个接口：业务规范到约束、约束到 witness generator、协议消息到 Fiat–Shamir transcript、数学群元素到字节解析和 verifier API。

一、欠约束：证明了错误的语言

设业务想证明 ，实际电路实现 。安全所需的不是“诚实 witness 能通过”，而是：

形式化定义与接口

实现安全要求以下映射一致：业务规范 →\to→ 源程序 →\to→ 电路/约束 →\to→ prover/verifier 字节接口。底层 proof system 的知识可靠性只保证“存在满足已实现约束的见证”；如果约束集合 CimplC_{\mathrm{impl}}Cimpl​ 比预期关系 CspecC_{\mathrm{spec}}Cspec​ 更弱，则安全证明忠实保护的也是错误语言。

常见缺口包括：忘记 bit/range constraints、除法没有约束分母非零、数组索引未绑定、Merkle path 的方向位未布尔化、公开输出未连接回内部变量、optional branch 未约束未选分支。

攻击者不会使用诚实 witness generator

Prover 可以直接构造任意满足约束的 witness。因此“应用代码从不生成该异常值”不能修复欠约束；必须让约束本身拒绝。

二、Witness generator 与电路语义偏差

Generator 负责计算辅助变量，但它不是安全边界。需要检查：

  • 整数/域转换：负数、溢出、取模和截断与原程序一致。
  • 分支一致：所有条件选择器是布尔值，且分支输出确实由选择器约束。
  • 错误传播：解析失败、除零或查表失败不能悄悄填 0 后继续证明。
  • 公共输入布局：prover 与 verifier 对顺序、长度和编码完全一致。

三、Fiat–Shamir transcript 必须唯一绑定上下文

挑战应由规范编码的完整上下文产生：

协议标签、版本、曲线/域、verification key、公共输入、全部先前 commitments、参与方角色和会话都可能需要进入 transcript。每个挑战必须在其依赖的消息固定后派生；challenge-to-field 应定义宽度、字节序、模约减或 rejection sampling。

四、数学对象必须有规范字节表示

对象必须检查遗漏后果
域元素长度、字节序、值小于模数同一元素多种编码，transcript 分叉
椭圆曲线点解码、在曲线上、非无穷远、正确子群invalid-curve / small-subgroup 与 pairing 异常

公共输入数量上限、类型与顺序遗漏或错绑业务字段

五、随机数、blinding 与可信设置

  • Prover blinding/nonce 必须不可预测且不跨证明复用；确定性派生需绑定 witness、statement 和域。
  • Structured setup 应记录 circuit/degree、参与者贡献、transcript 验证和参数哈希；不能只保存最终文件。
  • Verifier 不应接受来自不匹配曲线、协议版本或 circuit 的 key/proof。
  • Witness-dependent 标量乘、FFT 和 MSM 是否需要 constant-time，取决于本地对手与侧信道模型。

从关系规范生成负向测试

对每个业务谓词，至少构造一组“只违反这一条件”的 witness：范围上界多一、分母为零、Merkle 方向位非布尔、公开输出替换、数组索引越界、未选分支填入任意值。若这些 witness 中任何一个仍被约束接受，就应先修复关系，而不是继续调试 proving key 或优化 prover。

测试还要区分三种失败：witness generator 拒绝异常输入、约束系统拒绝异常赋值、verifier 拒绝畸形字节证明。第一种只是诚实路径行为，不能替代后两种安全边界；攻击者可以绕过 generator 直接构造满足约束的赋值，也可以直接向 verifier 提交任意编码。

从一句需求推导正向与负向关系测试

需求为“公开哈希 对应一个私有 8 位值 ”。正确关系至少包含：、 与每个 。若只写重组等式而遗漏布尔约束，证明者可在域中选择任意 拼出超范围值；证明系统的 soundness 仍然成立，因为它证明的本来就是那个错误语言。

测试预期发现的问题
合法 8 位值与正确哈希接受基本完备性
但伪造非布尔分解拒绝范围欠约束
合法 witness，替换公开 拒绝公共输入未绑定
同一证明换 circuit/version/domain拒绝transcript 域分离不足
非规范域元素或群元素编码拒绝parser 与代数语义不一致

测试 witness generator 的输出与测试 verifier 都不够：两者可能共享同一个错误假设。应从独立的关系规范生成拒绝样例，并在原始 witness、约束 trace、序列化证明和应用层公开输入四个边界分别断言。

六、证明之外需要什么验证

NEGATIVE WITNESS TESTS主动寻找异常满足解

篡改每个辅助变量、边界值、分支位和公共输入，确认约束拒绝。

DIFFERENTIAL TESTING原程序与域模型对拍

在正常、边界和随机输入上比较输出与错误语义。

FUZZ PARSERS畸形 proof/public input

覆盖非规范编码、长度截断、重复字段和跨版本输入。

CLAIM–EVIDENCE MAP区分证明与测试覆盖

cryptographic proof、functional tests、fuzzing 和 constant-time audit 互不替代。

代码库、测试和审计报告是实现证据，不是协议安全证明；论文也不能用 benchmark 代替 threat model 和 reduction。相反，形式化论文结论也不覆盖未经分析的 parser、FFI、序列化与并发实现。

一句话总结：零知识实现的最终安全对象是“verifier 实际接受的字节串所定义的关系”，而不是论文中的理想等式；必须逐接口证明并测试它与业务规范一致。

七、从安全审计到测试验证

SPECIFICATION

关系完整性

每个业务谓词都应对应可定位的约束，并有负向测试。

TRANSCRIPT

上下文唯一性

协议、曲线、VK、statement、轮次与全部消息要按唯一顺序哈希。

ENCODING

规范解析

拒绝非规范 field/group 编码、非法点、小子群点和长度歧义。

ASSURANCE

证据分层

单元测试、差分测试、模糊测试、形式化验证和密码学证明提供不同层次证据。
