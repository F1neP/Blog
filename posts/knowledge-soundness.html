Knowledge Soundness 与现代证明系统

LEARNING NOTE · PROOFS OF KNOWLEDGE

普通 Soundness（可靠性）只保证“假命题难以骗过验证者”；Knowledge Soundness（知识可靠性）进一步要求：一个能让验证者接受的 Prover（证明者），应当真的掌握使关系成立的 witness（见证）。

一句话记忆：Soundness 排除假命题；Knowledge Soundness 从成功证明者中提取 witness。

必要背景

Soundness（可靠性）阻止假命题被接受；Zero-Knowledge（零知识）限制验证过程泄露的信息；Knowledge Soundness 则要求成功证明者对应一个可提取 witness。Interactive Proof（交互式证明）和 Simulator（模拟器）的完整定义可分别参阅复杂性与交互证明和交互式零知识证明。

一、普通 Soundness 还缺少什么？

设语言由 NP relation（NP 关系）R 定义：

x 是公开 statement，w 是秘密 witness；R(x,w) 可在多项式时间内验证。

普通 Soundness 关注 x∉LR 的情况：命题为假时，任何作弊证明者 P* 都不应以显著概率说服验证者。

但当 x∈LR 时，普通 Soundness 不再约束 P* 的“知识来源”。验证者接受，只能说明交互满足了验证条件；它没有自动给出一个算法，证明 P* 内部确实拥有 w。

THE GAP“命题是真的”与“这个人知道证据”不是同一句话

例如，公开钥匙 y 的确对应某个私钥 w，因此“存在 w 使 y=f(w)”是真命题。普通 Soundness 不能单独排除某个参与者转发别人的证明、利用并发会话拼接消息，或通过协议漏洞在并不知道 w 的情况下获得接受。

二、Knowledge Soundness 与 Extractor

Knowledge Soundness 通常通过 Extractor（Knowledge Extractor，知识提取器）E 定义。量词应覆盖任意高效作弊证明者 P* 及其辅助输入；在黑盒定义中，E 通过 oracle 方式运行、重启或回退 P*，在非黑盒定义中则可能使用 P* 的代码。具体模型必须明确，不能把 rewinding 当作所有证明系统默认支持的能力。

κ 是 Knowledge Error（知识误差）。具体提取概率和运行时间因定义与协议而异；核心含义是“超过知识误差的成功率必须对应可提取知识”。
01
OBSERVE

让 P* 产生可接受证明

Extractor 以验证者接口同 P* 交互，观察其能否以超过 κ 的概率通过验证。

02
REWIND / FORK

固定关键前缀，改变挑战

在具有 Special Soundness（特殊可靠性）的三轮协议中，E 可回退到同一条第一消息之后，发送不同挑战，收集两份有效响应。

03
EXTRACT

由多份响应计算 witness

协议的代数结构保证：同一承诺下对不同挑战都能正确回答，就暴露了足以恢复 w 的信息。

Simulator（模拟器）与 Extractor：都会回退，但方向相反

对象它没有什么它要生成什么证明哪项性质
Simulator S没有 witness w与真实 Verifier View 不可区分的模拟视图Zero-Knowledge

两种“回退”的用途

Simulator 回退，是为了猜中验证者挑战并伪造一份合法视图，说明验证者没有学到额外知识；Extractor 回退，是为了让同一证明者回答不同挑战，再把 witness 算出来，说明成功证明者确实掌握知识。

必要条件

提取公式依赖协议的具体代数条件，例如 z₀ 必须可逆、输入要属于规定群、statement 与 witness 必须绑定到同一会话。Knowledge Soundness 不是看到“有交互”就自动获得的性质。

四、证明系统不是一条单线，而是一组属性坐标

Interactive Proof、Zero-Knowledge、NIZK（Non-Interactive Zero-Knowledge，非交互式零知识）、SNARK（Succinct Non-Interactive Argument of Knowledge，简洁非交互知识论证）、STARK（Scalable Transparent Argument of Knowledge，可扩展透明知识论证）和 Bulletproofs（防弹证明）并非依次淘汰前者的版本；它们是在交互性、证明长度、验证成本、设置假设和知识可靠性等属性上的不同组合。

Proof（证明）与 Argument（论证）的区别

PROOF信息论可靠性

Soundness 通常要求即使 Prover 计算能力无限，也难以证明假命题。

ARGUMENT计算可靠性

只要求概率多项式时间 Prover 无法破坏 Soundness，通常依赖密码学假设。

ARGUMENT OF KNOWLEDGE计算型知识提取

除计算可靠性外，还要求从高效成功证明者中提取 witness。

因此 SNARK 的全称里是 Argument of Knowledge，而不是无条件的 Proof of Knowledge：

五、发展脉络：动机改变了哪些属性？

1985 / 1989 Interactive Proof 与 Zero-Knowledge

Goldwasser、Micali、Rackoff 用随机交互定义 Completeness、Soundness 与 Knowledge Complexity（知识复杂度）；证明开始同时讨论“可信”与“少泄露”。

1988 Non-Interactive Zero-Knowledge（NIZK）

Blum、Feldman、Micali 研究共享随机串模型下的一次性证明：减少在线往返，便于存储、转发与公开验证，但必须明确设置模型。

1992 Proof of Knowledge 的形式化

Bellare 与 Goldreich 系统讨论 Knowledge Error、Extractor 运行时间等定义问题，使“证明者知道 witness”成为可验证的数学性质。

1990s–2010s Succinct Arguments 与 SNARK

研究目标进一步加入短证明和快速验证。Groth16 是典型配对型 SNARK：证明很短、验证高效，但具体系统依赖结构化参考串和相应代数假设。

2018 Bulletproofs 与 STARK

Bulletproofs 以 Inner-Product Argument（内积论证）实现无可信设置的短证明；STARK 强调 Transparent Setup（透明设置）、可扩展性与基于哈希的后量子安全路径。

现代系统对照：它们解决的重点并不相同

系统 / 技术主要目标交互 / 设置关键提醒

六、Knowledge Soundness 的必要性与选择方法

当系统的授权语义是“只有掌握某个秘密的人才能完成操作”时，仅证明 statement 为真通常不够。典型场景包括：

  • 身份认证：证明自己知道与公开钥匙对应的私钥，而不是只证明该私钥存在。
  • 数字资产：证明自己知道可花费某个承诺或账户的 Opening Information（打开信息）或 Secret Key（私钥）。
  • 匿名凭证：证明持有由发行方签发的 Credential（凭证），同时不泄露身份属性。
  • 密文关系：证明知道明文和随机数，使密文、承诺与公开 statement 绑定到同一 witness。
  • 可验证计算：证明知道满足约束系统的执行轨迹，而不是提交一份碰巧通过局部检查的数据。

选择证明系统时，不应只问“哪个最新”，而应依次确认：

1
SECURITY GOAL

到底要证明真实性、知识还是隐私？

先区分 Soundness、Knowledge Soundness 与 Zero-Knowledge；它们互不自动蕴含。

2
TRUST MODEL

能否接受可信设置或 Random Oracle？

“非交互”“无可信设置”“公开可验证”是三项不同要求，必须分别写清。

3
COST MODEL

瓶颈是证明、验证、通信还是内存？

短证明不一定意味着 Prover 快；验证快也不等于设置简单。需要结合电路规模和部署环境比较具体成本。

4
ASSUMPTIONS

需要何种代数与后量子假设？

配对、离散对数、哈希函数和编码理论会带来不同的安全基础、证明大小和实现复杂度。

七、最终记忆框架

  • Soundness：假 statement 不能被作弊 Prover 高概率证明成功。
  • Knowledge Soundness：成功率超过知识误差的 Prover 对应一个能够输出 witness 的 Extractor。
  • Simulator：没有 witness，却能模拟 Verifier View，用于证明 Zero-Knowledge。
  • Extractor：访问成功证明者并恢复 witness，用于证明 Knowledge Soundness。
  • Proof / Argument：区别在于 Soundness 对无限算力还是仅对高效攻击者成立。
  • 现代系统：是在交互性、零知识、简洁性、设置模型、验证成本和后量子性等坐标上的不同组合。
一句话总结：Knowledge Soundness 的核心是，只要证明者以显著概率成功，就应当能够从其行为中提取有效 witness。
