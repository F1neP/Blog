NIZK 与 Fiat–Shamir：从随机挑战到非交互证明

LEARNING NOTE · NIZK · FIAT–SHAMIR

Non-Interactive Zero-Knowledge（NIZK，非交互零知识）希望把原本需要 Prover 与 Verifier 往返交互的零知识证明，变成一份可以独立发送和验证的 proof。Fiat–Shamir paradigm 解决的是其中一个关键步骤：对于 public-coin protocol，用哈希函数从已有 transcript 生成原本由 Verifier 随机选择的 challenge，从而消除在线交互。

NIZK 是一种证明系统目标；Fiat–Shamir 是一种去交互范式；Random Oracle Model 则是分析这一范式时常用的理想化模型。三者不能混为一谈。

一、为什么要从 Interactive ZK 走向 NIZK？

交互式零知识证明中，Verifier 的随机 challenge 是 soundness 的重要来源。一个典型流程是：

Prover 先发送第一条消息 ，Verifier 再随机选择 challenge ，Prover 根据 witness、随机性和 challenge 生成 response 。Verifier 最后检查：

这种结构的问题不是证明能力不足，而是Verifier 必须在线参与 challenge 生成。如果 proof 需要被存储、转发、公开验证，或者由很多独立 Verifiers 在不同时间验证，持续交互就不方便。

INTERACTIVEVerifier 在线出题

Challenge 在 Prover 固定第一条消息之后由 Verifier 随机生成。

NIZK一次生成 Proof

Prover 输出一份 proof，Verifier 之后只需读取公开输入和 proof 即可验证。

CORE QUESTION随机性从哪里来

去掉在线 Verifier 后，仍然必须保留原协议依赖的不可预测 challenge。

六、为什么 Completeness 保持？

Completeness 最直接。若 且诚实 Prover 持有有效 witness，那么每个并行实例都按照基础 ZK protocol 的诚实算法生成。

Fiat–Shamir 只改变 challenge 的来源，不改变基础 verification predicate。因此，只要基础 protocol 对任意合法 challenge 都满足 completeness，诚实生成的每个 transcript 仍会通过验证。

七、为什么 Soundness 依赖随机 Challenge？

交互式 protocol 的 soundness 依赖一个关键事实：Prover 在发送 时不知道 Verifier 之后会选择哪个 。因此 cheating strategy 很难只为某个预先选定的 challenge 准备 transcript。

该 ROM 构造通过两步恢复这一效果：

  • Parallel repetition：按基础协议的真实 challenge space 把 soundness error 降到 negligible。
  • Random Oracle：对已经绑定公开上下文和 first message 的新查询给出独立随机输出，从而承担原协议的随机 challenge。

“Program Random Oracle”属于安全证明，不属于真实协议

诚实 Prover 不能指定哈希输出，也不能“先选 challenge 再倒推 Hash”。可编程 Random Oracle 是 Simulator 在理想化安全实验中使用的证明能力，用于解释为什么真实 proof 不泄露 witness；严格证明还需处理该查询此前已被 adversary 查询的事件。

如果 Simulator 可以对多个此前未查询的新输入进行这种 programming，还可以进一步研究 many-instance simulation、multi-theorem 与 adaptive ZK；这些结论仍取决于精确安全实验。

九、换成现实 Hash 后发生什么？

这一节是整篇最重要的安全边界。Lecture 19 明确指出：

在 Random Oracle Model 中， 被理想化为真正随机且可由 Simulator 编程的 oracle。现实中我们会部署某个固定、显式的哈希函数，但这并不自动继承 ROM 中的全部证明性质。

这里需要分别注意两个风险：

性质ROM 中的证明工具换成显式 Hash 后的问题
Zero-KnowledgeSimulator 可以 program RO，使完整公开上下文与 a 对应的查询映射到 e固定 Hash 一般不能按模拟需要自由编程。
Soundness新输入上的随机 oracle 输出承担随机 challenge并不存在“任何 public-coin protocol + 任意 Hash 都安全”的一般结论。

Lecture 19 进一步提醒：某些多消息 protocol 即使使用 Random Oracle 也可能失去 soundness；对于只具有 computational soundness 的协议，也存在 Fiat–Shamir 不安全的反例。因此，Fiat–Shamir 应被理解为一个需要针对具体 protocol 与安全模型证明的范式，而不是无条件安全的机械步骤。

这也是本文不写“Fiat–Shamir 保证非交互安全”的原因

准确说法应当是：对于满足相应结构条件的 public-coin protocol，可以研究用 Fiat–Shamir 消除交互；其安全性取决于底层 protocol、采用的模型以及具体实例化证明。

十、几个最容易混淆的概念

概念它解决什么不要误解成什么
NIZK一类非交互、满足 ZK 与 soundness 等定义的 proof system。不是某一个固定 transform。
Fiat–Shamir把 public-coin Verifier 的随机 challenge 改为 transcript-derived hash challenge。不是 NIZK 的定义。
Random Oracle Model把 Hash 理想化为真正随机 oracle，并允许安全证明中的 Simulator 编程。不是现实哈希函数本身。
CRSNIZK Setup 输出的公共参考信息。不是 witness，也不是每次 proof 的随机 challenge。
HVZK Simulator模拟面对诚实随机 Verifier 时的基础 transcript。不能单独解释 Fiat–Shamir transcript 的哈希一致性。
Programmable RO让 NIZK Simulator 把模拟 challenge 与绑定完整公开上下文的哈希查询对齐。不是现实 Prover 可以操纵 Hash。

十一、它在后续证明系统中的位置

Fiat–Shamir 的价值不仅出现在经典 ZK。Lecture 20 特别强调 Sumcheck 是 public-coin protocol，因为 Verifier 每轮只发送均匀随机 field elements。因此，后续很多 succinct proof systems 都会再次遇到同一个结构问题：

这解释了为什么学习路线中，NIZK 与 Fiat–Shamir 应放在 Interactive ZK 之后、Sumcheck 与 GKR 之前：它先建立“怎样把随机挑战非交互化”的一般认识，后面再看到 Sumcheck、GKR、Polynomial Commitment 组合成 succinct argument 时，就不会把 Fiat–Shamir 当成一个突然出现的黑箱步骤。

与后续文章的关系

Sumcheck 负责逐轮压缩低度多项式求和声明，GKR 把整个分层电路逐层归约，Polynomial Commitment 负责绑定并打开多项式随机点评估。后续《从 GKR 到 SNARG》将再把这些组件与 Fiat–Shamir 放到同一条完整构造链中。

NIZK目标

Proof 可以独立发送和验证，同时满足相应的 soundness 与 zero-knowledge 定义。

FIAT–SHAMIR变换

用哈希生成 public-coin challenge，从而去掉在线 Verifier 消息。

ROM证明模型

把 Hash 看成随机且可编程的 oracle，用于建立 soundness 与 simulation 论证。

  • NIZK 不等于 Fiat–Shamir：前者是 proof-system 概念，后者是去交互范式。
  • Challenge 没有消失：只是从 变成由完整 transcript context 的哈希导出。
  • 时间顺序仍然重要： 必须先固定，challenge 才能由其确定。
  • ROM simulation 的核心是 programming：先模拟 ，再编程绑定公开上下文与 a 的 Random Oracle 查询。
  • Programming 不是现实攻击能力：它只存在于安全证明的 idealized oracle experiment。
  • 显式 Hash 不是自动安全：具体 Fiat–Shamir 实例化必须结合底层 protocol 与模型单独分析。
一句话总结：NIZK 要求 Prover 一次生成可独立验证且不泄露 witness 的 proof；Fiat–Shamir 通过把 public-coin Verifier 的随机 challenge 改写为 transcript 的哈希值来消除在线交互，而其安全性分析依赖底层 protocol 与所采用的 Random Oracle 或其他具体模型。
