zkVM：从指令执行轨迹到可验证程序

PROOF SYSTEMS · VERIFIABLE VIRTUAL MACHINES

zkVM 让开发者证明某个程序在给定输入和初始状态上执行并产生输出，而不必手写整张业务电路。它并没有消除算术化：复杂性被下移到 ISA、CPU transition、内存一致性、syscall 和程序/输入承诺的统一约束。

为什么需要这一章？

手工把每个程序改写为专用电路既昂贵又容易引入语义错误。zkVM 固定一套指令语义，让开发者证明执行轨迹而不是重写业务电路；代价是必须额外约束取指、内存、范围与状态转移，本章说明这种抽象真正省下了什么、又新增了什么。

贯穿例子

考虑程序：从地址 0 读入 7，加常数 5，再写到地址 1。CPU 表可含列 (pc,opcode,src,dst,value)(pc,opcode,src,dst,value)(pc,opcode,src,dst,value)：三行的 pcpcpc 依次为 0、1、2，最终输出为 12。memory 表还要包含访问元组 (addr,time,value,isWrite)(addr,time,value,isWrite)(addr,time,value,isWrite)，排序或置换后检查：每次读的值等于同地址最近写入值。

若遗漏 time/order 约束，证明者可能让 LOAD 读取一次未来写入的 7；每行数值看似合法，执行语义却错误。这个例子体现 zkVM 的主要难点是全局一致性而非单个加法门。

  • 地址改变时使用初始内存值；

只证明每次访问的地址和值“出现过”不够，必须证明时序与 last-write-wins 语义。

五、分段证明与递归聚合

01Segment execution把长程序切成固定步数 chunks
02Prove segments每段绑定 entry/exit state
03Link states证明前段输出等于后段输入
04Recursive aggregate压缩为短最终 proof

并行 segment proving 能改善吞吐，但 state-linking、program identity、segment index 和总步数必须进入递归 statement；否则可重排、遗漏或拼接来自不同执行的有效段。

六、zkVM 的四层正确性

层需要保证不由下一层自动覆盖
应用程序业务逻辑、输入验证和算法正确zkVM soundness
编译/运行时源程序到 binary、syscall 语义一致ISA trace 约束
VM arithmetizationCPU、memory、I/O 约束完整底层 PCS/FRI/SNARK
Proof system承诺、低度、知识可靠性与 ZK实现 parser、随机性和侧信道
三类关键安全边界
  • 程序未绑定：证明了攻击者选择的另一份 binary 的正确执行。
  • syscall 被当作可信 oracle：外部 I/O 或加速器结果没有进入约束。
  • Soundness 与隐私混淆：能验证执行不代表 trace 或输入默认零知识；透明 STARK 也需专门 masking。
一句话总结：zkVM 把“程序正确执行”拆成 CPU transition、跨表事件和内存时序约束，再用证明系统压缩整张轨迹；它减少应用手写电路，却把安全责任扩展到 ISA、编译、运行时和递归链接。
